## Privacy, access, and dependencies

**F01 · P1 · Administrative guest fields are serialized into the guest browser.** `getRsvpContext` selects complete guest rows, and the RSVP page passes them into a client component. That includes internal notes, relationship/VIP metadata, accessibility and hotel fields whether or not the UI renders them. Return an explicit guest-facing projection/DTO and verify both HTML and RSC payloads exclude administrative fields. Evidence: `lib/data/rsvp.ts:16`, `app/(guest)/rsvp/h/[token]/page.tsx:54`, `supabase/migrations/0001_init.sql:72`.

**F02 · P1 · Re-inviting an existing owner can remove the last owner.** The invitation path upserts a requested role without the last-owner guard used by ordinary role changes. The UI encourages re-inviting to update a role. An isolated execution of the actual invitation function with a sole-owner fixture left zero owners after inviting that email as editor. Use one transactional membership operation for invite/update/remove and serialize competing owner changes. Evidence: `lib/data/members.ts:107`, `lib/data/members.ts:130`, `components/admin/TeamManager.tsx:53`.

**F03 · P1 · Admin refresh cookies have no persistence path on page reads.** The Supabase server client catches failed cookie writes in Server Components and says middleware handles refresh, but the repo has no proxy/middleware. This can produce premature logouts after token expiry. Implement supported request/response cookie refresh in Next 16's proxy and test an expired-token navigation. Evidence: `lib/supabase/server.ts:13`; installed `node_modules/@supabase/ssr/src/createServerClient.ts:43`. [Supabase's SSR guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client) confirms that a proxy is needed because Server Components cannot write cookies.

**F04 · P1 · Installed production dependencies have unresolved advisories.** The registry audit flags Next **16.2.10**, its nested nanoid/PostCSS, sharp, and xlsx **0.18.5**. Next's Server Action denial-of-service advisory directly matches this app's architecture; other advisories have usage-dependent reachability and were not exploited. Select a currently patched compatible Next release, refresh the lockfile, and verify the resulting dependency graph. Audit suggested 16.3.4; 16.2.11 fixes the cited individual Next advisory but is not asserted to clear every transitive advisory. xlsx reports no npm-registry fix; choose a maintained distribution or replacement and verify workbook import/export compatibility. [Next's advisory](https://github.com/vercel/next.js/security/advisories/GHSA-m99w-x7hq-7vfj) identifies the affected range; [SheetJS installation guidance](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/) documents its own release distribution. No packages were updated during this audit.

## RSVP and household truth

**F05 · P1 when events differ · Guest attendance and meal controls overwrite every event together.** A guest cannot accept reception but decline rehearsal: `setAttending` assigns one value to every invited event. `setMeal` similarly copies one meal ID across events, and the menu includes all wedding meals. Review shows one collapsed attendance/meal summary. Render and validate per-event responses, allowing global meal options only where appropriate. Evidence: `components/guest/RsvpFlow.tsx:91`, `:101`, `:324`, `:485`.

**F06 · P1 · “Confirmed” does not prove a complete RSVP.** SQL derives completeness from stored response rows rather than the expected invited guest/event combinations. Missing rows are not counted as pending, and an empty response set can become completed, contrary to the pure helper. Conversely, the UI advances to confirmed for any successful save even if its returned status is still started. Unanswered guests are displayed as declining on review because it tests only for any `yes`. Define expected answers once, reject incomplete final submission, and render the actual accepted outcome. Evidence: `supabase/migrations/0009_responses_require_invites.sql:173`, `lib/domain/invitation-rules.ts:141`, `components/guest/RsvpFlow.tsx:153`, `:486`.

**F07 · P1 · Admin corrections regress completed RSVPs.** Admin response writes always send `complete:false`, so correcting a meal can turn a completed household into started; entering a complete phone RSVP may never complete it. Preserve completion for corrections unless new unanswered requirements are introduced, and support explicitly completing a phone response. Evidence: `app/admin/(dashboard)/guests/actions.ts:153`, `supabase/migrations/0009_responses_require_invites.sql:183`.

**F08 · P2 · Guest/event changes leave household status stale.** Adding/removing guests, adding invitations, and deleting events do not consistently recompute status. Completed households can retain unanswered new requirements; started households can remain started after their only pending requirement is removed. Recompute all affected households transactionally on every change. Evidence: `lib/data/guests.ts:44`, `:118`, `lib/data/events.ts:299`, `:400`; invitation removal does have a recomputation at `:467`.

**F09 · P2 · Disabled RSVP events can keep households incomplete forever.** Guest context hides events with `rsvp_enabled=false`, but completion counts their invite-backed pending rows. The write RPC also checks an invite without checking that RSVP is enabled. Use the same active-requirement definition for context, writes, completeness, and reminders, retaining old answers separately as history. Evidence: `lib/data/rsvp.ts:29`, `supabase/migrations/0009_responses_require_invites.sql:136`, `:173`.

**F10 · P2 · Removing or renaming a plus-one after autosave does not reconcile the saved guest.** Continue persists new plus-ones. Going back and removing one only changes the local array; the stored guest remains. Changing its name breaks name-based deduplication and may create another guest or hit the cap. A first-name-only plus-one is also shown in meals/review but omitted from the submitted new guests, which require both names. Return stable guest IDs after autosave and support explicit update/remove operations; use identical completeness rules in preview and payload. Evidence: `components/guest/RsvpFlow.tsx:119`, `:168`, `:239`, `:500`, `lib/domain/invitation-rules.ts:92`.

**F11 · P2 · Parallel plus-one submissions can exceed invitation limits.** Deduplication and count reads happen before inserts without a household row lock. Two browser tabs can both see the same free slot. Lock and enforce cap/deduplication inside the SQL transaction using a stable request/guest identity. Evidence: `lib/data/rsvp.ts:54`, `:81`, `supabase/migrations/0009_responses_require_invites.sql:79`.

**F12 · P2 · Editing household limits can lock guests out of further RSVP edits.** Normalization uses named guest count but does not protect already-created plus-ones. Reducing plus-one slots below that count means future submissions reject, even for an existing guest's meal correction. Validate proposed limits against all existing guests and explain incompatible changes before saving. Evidence: `app/admin/(dashboard)/guests/actions.ts:70`, `lib/domain/invitation-rules.ts:49`, `:77`.

**F13 · P2 · Closed RSVP and seat-reveal behavior is incomplete.** Completed households still see editable controls after the deadline, while every save is rejected. Non-completed households return the closed shell before showing their table. The page also reveals only the first seated household member at the first published event, hiding other members' assignments. Provide an explicit read-only response summary after close and a per-person/per-event table view that remains available on wedding day. Evidence: `components/guest/RsvpFlow.tsx:174`, `app/(guest)/rsvp/h/[token]/actions.ts:32`, `app/(guest)/rsvp/h/[token]/page.tsx:31`.

**F14 · P2 · The guest write boundary lacks full relationship/payload validation.** An existing meal ID is not checked for the current wedding/event. Question answers similarly lack complete active/type/scope/guest ownership validation. Add runtime payload schemas and database relationship checks; TypeScript alone does not validate a submitted server-action payload. Question impact is currently dormant if migration 0014 is deployed, because the questions were intentionally retired. Evidence: `supabase/migrations/0009_responses_require_invites.sql:116`, `:139`, `:160`, `lib/domain/invitation-rules.ts:25`.

## Reports, guest lists, and seating

**F15 · P1 for multi-event handoffs · Reports and printed cards can mix events.** The common table lookup selects a guest's first seat across all events; several reports select their first meal, and caterer inclusion is attendance at any event. Place cards also group by table name across events. The Meals page repeats the same seat lookup mistake. Require an event for operational output, join on guest plus event, and group by table ID. Evidence: `app/api/export/[report]/route.ts:63`, `:94`, `:194`, `:213`; `app/admin/print/place-cards/page.tsx:26`; `app/admin/print/escort-cards/page.tsx:21`; `app/admin/(dashboard)/meals/page.tsx:30`.

**F16 · P1/P2 · CSV output lacks formula protection and complete escaping.** Guest-controlled names/dietary fields can be emitted as spreadsheet formulas. Headers are joined without escaping, so an event called “Reception, Dinner” creates extra columns. Carriage returns are also not quoted. Use one tested serializer for headers and values, neutralize formula prefixes, and keep XLSX text typed as text. Isolated execution reproduced a raw `=1+1` cell and raw CR. Evidence: `app/api/export/[report]/route.ts:228`.

**F17 · P2 · Failed queries become apparently valid empty reports/counts.** Export loading ignores six query errors and substitutes empty arrays; metrics and guest context have similar patterns. A failed response read can make everyone look pending or produce an empty caterer file. Export exceptions become `404 unknown report`, while household detail treats every exception as not found. Check each query, validate report names before reads, show retryable failures, and never label partial data as a complete report. Evidence: `app/api/export/[report]/route.ts:30`, `:264`; `lib/data/metrics.ts:32`; `lib/data/rsvp.ts:14`; `app/admin/(dashboard)/guests/[householdId]/page.tsx:45`.

**F18 · P2 · Two silent row limits can hide real guests and answers.** Guests search defaults to 200 households before client filters/search. Bulk reads have no pagination, while repository Supabase config caps responses at 1,000 rows. Several events can hit that ceiling with far fewer than 1,000 guests. Guest RSVP currently reads all wedding responses before filtering to one household. Implement accurate pagination/counts and narrow the guest query; page bulk exports or aggregate in SQL. Current production counts/limit are unknown. Evidence: `lib/data/households.ts:57`, `app/admin/(dashboard)/guests/page.tsx:40`, `lib/data/rsvp.ts:23`, `supabase/config.toml` (`max_rows`).

**F19 · P2 · Admin meal clearing fails, and menus cross event boundaries.** Selecting the empty option passes null, but null-coalescing restores the old value. The selector also filters by age, not event. Distinguish undefined from explicit null and filter/validate by event. Evidence: `components/admin/ResponseCell.tsx:21`, `:42`, `:48`; `app/admin/(dashboard)/guests/[householdId]/page.tsx:136`.

**F20 · P2 · “No table” means no seat anywhere, not missing a required event seat.** A guest seated for rehearsal but unseated for reception disappears from this queue. Compare live attending guest/event pairs with matching assignments. Evidence: `lib/data/households.ts:95`, `:105`, `:138`.

**F21 · P2 · Seating a household can partially commit.** Guests are assigned in separate writes; a later failure leaves earlier assignments committed while the optimistic UI reverts. The error copy claims nothing changed when the network result is ambiguous. Use an atomic group assignment and refetch after uncertain outcomes. Evidence: `app/admin/(dashboard)/seating/actions.ts:121`, `components/admin/SeatingCanvas.tsx:189`. Budget's generic network error makes the same unsupported “nothing was changed” claim at `components/admin/budget/BudgetTable.tsx:206`.

**F22 · P2 · Capacity and live seating eligibility are not enforced server-side.** Client capacity checks are based on stale local counts; the data layer validates ownership/event but does not enforce available chairs or current invitation/attendance. Two planners can take the last chair concurrently. Lock the destination table and validate a whole requested move before committing. Evidence: `components/admin/SeatingCanvas.tsx:286`, `lib/data/seating.ts:153`.

**F23 · P2 · Declined/uninvited guests silently occupy chairs.** Headline seating counts exclude nonattendees while table occupancy includes stored assignments, without explaining those stale seats. Flag the discrepancy and offer reviewed cleanup; preserve manual placements until confirmed. Evidence: `components/admin/SeatingCanvas.tsx:129`, `:132`, `:715`.

**F28 · P2 · Failed new-payment entry loses the draft; Enter bypasses the button's pending guard.** The form clears fields before the asynchronous outcome and the submit function itself does not check pending. ## Communications and delivery

**F30 · P1 · “Hasn't responded” excludes started households.** Audience resolution asks household search for pending only, then tries to include started after they have already been removed. Use one pending-and-started eligibility function shared by dashboard, review, and send. Evidence: `app/admin/(dashboard)/comms/actions.ts:41`, `lib/data/households.ts:113`.

**F31 · P2 · The reminder cooldown is not enforced by sending.** The displayed recommendation uses seven days; the actual campaign audience does not. The recommendation also treats queued/failed/no-email recipients as recently reminded. Base eligibility on actual accepted sends, contactability, status, deadline, and cooldown, and use it everywhere. Evidence: `lib/data/comms.ts:123`, `app/admin/(dashboard)/comms/actions.ts:41`.

**F32 · P1 · Campaigns/test sends can report success after provider rejection.** Email sending returns `{id:null}` on Resend error; callers ignore it and the composer reports the reviewed count as sent. Missing credentials also invoke the local HTML-file fallback even in production. Return explicit accepted/failed outcomes, fail clearly on missing production configuration, and display actual counts and reasons. Evidence: `lib/email/send.ts:19`, `:39`; `app/admin/(dashboard)/comms/actions.ts:112`, `:139`; `components/admin/CampaignComposer.tsx:64`.

**F33 · P1 before bulk/scheduled sending · Campaigns cannot safely resume.** Every recipient is sent sequentially inside the originating request. A timeout leaves a partial campaign; repeating the action creates a new campaign and can resend the successful portion. Make recipients a durable outbox with stable delivery keys, bounded claims/batches, recorded attempts, retries, and a resume path. Backgrounding the same loop alone is not durable recovery. Evidence: `app/admin/(dashboard)/comms/actions.ts:130`.

**F34 · P2 · No-email, bounced, complained, and failed recipients need real outcomes.** All selected households are inserted queued, including those never sent because they lack email. Later campaigns ignore bounce/complaint suppression. Persist skipped/failed/suppressed outcomes, surface contact-repair tasks, and retry only eligible failed recipients. Evidence: `lib/data/comms.ts:40`, campaign audience/sending in `app/admin/(dashboard)/comms/actions.ts`.

**F35 · P2 · Campaign review pins only a count, not the reviewed message/recipients.** The token encodes count/audience/type. Changed identities, email addresses, or content with the same count are not detected. Persist a reviewed draft containing recipient/address snapshot, content version/hash, and expiry. Send that exact approved draft or require re-review. Evidence: `lib/domain/campaign-review.ts:15`; isolated helper inspection/reproduction confirmed no recipient/content inputs exist.

**F36 · P2 · Save-the-date/thank-you choices have no dedicated templates.** Only invitation/reminder branches are templated. Other offered types can produce a reminder subject, blank body, and RSVP CTA when fields are left empty. Implement localized templates or clearly require custom fields. Escape custom subject/body at HTML boundaries rather than interpolating untrusted markup. Evidence: `components/admin/CampaignComposer.tsx:87`, `app/admin/(dashboard)/comms/actions.ts:50`.

**F37 · P2 · Delivery webhooks can lose updates or regress status.** Database errors are ignored and acknowledged with 200; a callback arriving before message-ID persistence is unmatched and lost. Status progression is a read-then-write operation, so concurrent delivered/opened events can downgrade the final state. Persist webhook events with deduplication, retry unmatched records, propagate database failures, and update status atomically. Evidence: `lib/data/comms.ts:71`, `:95`; `app/api/webhooks/resend/route.ts:61`.

**F38 · P1 configuration check / P2 code defect · Webhook verification fails open without a secret.** Verification is conditional on `RESEND_WEBHOOK_SECRET`; without it unsigned events with known message IDs can alter status. Reject unconfigured production webhook requests. Actual production secret presence is unknown. Evidence: `app/api/webhooks/resend/route.ts:36`.

**F39 · P2 · Confirmation delivery is coupled to an already-saved RSVP.** After commit, hotel lookup/email runs inside the same try block. A thrown failure returns “unknown” although the RSVP saved; retries can issue another confirmation. Provider rejections may instead be silently ignored. Save an idempotent confirmation job with the response and return the truthful saved result independently of delivery. Evidence: `app/(guest)/rsvp/h/[token]/actions.ts:35`.

## Save-the-Date sync and imports

**F40 · P1 before auto-apply · Shared household email can auto-match the wrong family.** Matching uses the first exact email match without checking uniqueness across households. A source-level probe matched Beth's submission to Alice because both had the same family email and Alice came first. Require a unique distinct household match; ambiguous email goes to review with names/context. Evidence: `lib/sync/match.ts:201`, `lib/sync/run.ts:115`.

**F41 · P1 · Sync writes and undo history are not atomic.** Household updates precede submission resolution/history. If the latter fails, a retry may record an empty patch because the data already changed, losing original undo values. Concurrent admin changes can also be overwritten between read and write. Lock/conditionally update the submission and household together, preserving before/after values and source precedence in one transaction. Evidence: `lib/sync/run.ts:118`, `app/admin/(dashboard)/imports/review-actions.ts:25`.

**F42 · P1/P2 · Repeating a review action can duplicate households or replace undo history.** Create/match paths check existence but not a still-pending state; creation precedes resolution. Two tabs or a retry after a partial failure can create a second invitation. Claim pending work atomically and enforce one resolution operation per source item. Evidence: `app/admin/(dashboard)/imports/review-actions.ts:70`.

**F43 · P2 · Edits to existing Sheet responses can be silently ignored.** Row identity hashes timestamp/email/name, not contact/address/notes content. Changed addresses or opt-out text can keep the same key; resolved rows are skipped, and pending raw review data is not refreshed. Keep stable source identity separate from content version/hash; show changed submissions as reviewable differences without undoing earlier human decisions. Evidence: `lib/sync/sheet.ts:54`, `lib/sync/run.ts:88`. A source-level probe confirmed unchanged keys after address/notes edits.

**F44 · P2 · Negated opt-out text can decline a household.** `/opt.?out/i` matches “Please do not opt out; I will attend.” The resulting flag can move pending to declined. Use a structured form answer or human review for free-text intent. Evidence: `lib/sync/sheet.ts:115`, `lib/sync/apply.ts:103`; reproduced with the actual parser.

**F45 · P2 · The advertised no-op duplicate sync is not concurrency-safe.** `upsertMany` reads existing rows and then inserts; simultaneous runs can collide on the unique key. Duplicate source rows within one batch can also fail insertion. Dedupe batches, use conflict-safe insert, and claim runs/submissions before applying. Evidence: `lib/data/submissions.ts:23`, `supabase/migrations/0010_sheet_submissions.sql:25`.

**F46 · P2 · Sync health and first-use controls are missing.** “Connected” is inferred from environment-variable presence rather than a successful run. Cron outcomes are not persisted, so repeated failures are invisible in the app. The review component, which contains the status/manual-check UI, disappears when there are no pending/applied submissions. A CSV fallback action exists but is not connected to a UI. Always display integration status, last successful sync, stale/error state, manual retry and CSV fallback. Evidence: `app/api/cron/save-the-date/route.ts:32`, `app/admin/(dashboard)/imports/page.tsx:85`, `:100`; `components/admin/ReviewInbox.tsx:79`; `imports/review-actions.ts:183`.

**F47 · P2 · New import runs do not reconcile existing households.** Replay protection covers the same import run, not uploading the same or corrected file as a new run. New runs insert new invitations; retrying partial/skipped rows can split a previously imported household. Add file/source fingerprints and explicit new/append/update/conflict decisions with a diff preview. Do not auto-merge families from fuzzy names. Evidence: `supabase/migrations/0009_responses_require_invites.sql:298`, `lib/data/imports.ts:46`, `components/admin/import/DoneStep.tsx:42`.

**F48 · P2 · Structural CSV errors are thrown away.** The parser returns data/headers but discards PapaParse diagnostics. An unterminated quoted cell can swallow subsequent guest rows; the domain validator never receives the structural error. Block or explicitly resolve fatal quote/field-count errors before proceeding and retain original row numbers. Evidence: `lib/csv/parse.ts:4`; isolated parser probe reproduced `MissingQuotes` with the next guest folded into the previous cell.

**F49 · P2 · Some guest/household creation paths partially commit.** Household, guests, invitations, and audit records are separate operations; later errors can leave earlier records saved and retries can duplicate them. Guest creation also ignores some response/lookup errors. Extend the transaction/idempotency pattern beyond CSV commit to these paths. Evidence: `lib/data/households.ts:313`, `lib/data/guests.ts:45`.

**F50 · P2 · The pending export omits invited guests without response rows.** New households created through `createWithGuests` get invitations but no response placeholders. The pending report requires `rs.length > 0`, so they can disappear until first RSVP. Derive pending requirements from guests/invites or guarantee placeholders on every creation path. Evidence: `lib/data/households.ts:313`, `app/api/export/[report]/route.ts:140`.

## Reliability, usability, and operational gaps

**F51 · P2 · Redis environment variables currently do nothing.** Limiting and caching are implemented only as process-local Maps despite documentation promising an automatic Upstash switch. Limits reset across instances/restarts, invalidation only reaches one instance, and expired keys are not evicted. Implement atomic shared limits and an appropriate cache strategy; bound any local fallback explicitly. Evidence: `lib/limiter.ts:1`, `:11`; `lib/env.ts`; README's Upstash promise.

**F52 · P2 · Pages lack designed loading/error/recovery boundaries.** No app `error.tsx`, `loading.tsx`, or custom household not-found route exists. Several forms throw rather than returning actionable errors, and some component comments assume a recovery boundary that does not exist. Add route-appropriate loading/retry states and consistent action results while preserving unsaved values. Evidence: app file inventory; `components/admin/ConfirmButton.tsx:31`; `app/admin/(dashboard)/guests/[householdId]/page.tsx:45`.

**F53 · P2/P3 · A roughly 19 MiB decorative video is mounted on admin and guest surfaces.** `FilmBackdrop` unconditionally includes the video source; its poster is roughly 560 KiB. This is unnecessary transfer/power cost for routine phone use. Prefer an optimized poster for admin/mobile/reduced-motion and load any video only when appropriate. Merely hiding it with CSS does not prove the browser avoids downloading it; verify network requests. Evidence: `components/FilmBackdrop.tsx:10`, dashboard/guest layouts, measured `public/video/hero-v5.*` file sizes.

**F54 · P2/P3 · Keyboard, focus, and readable secondary text need completion.** Desktop seating registers only a pointer sensor and lacks the mobile assignment alternative. Several dialogs do not contain focus, underlying content stays keyboard reachable, and household/response inputs lack contextual labels. Small secondary text uses `--muted: #8a8f86` on cream; review contrast and increase legibility. Provide universal button/select assignment, shared accessible dialogs, labels, and measured contrast checks. ## Efficiency work with a clear payoff

- **Narrow guest entry/RSVP reads.** Name lookup currently loads full households with guests and admin metadata just to find candidates; RSVP loads wedding-wide answers for one household. Use minimal searchable projections and household/event-scoped response reads. This improves both privacy and query cost.
- **Batch Sheet matching data.** `lib/sync/run.ts:109` calls full `households.getDetail` per candidate, which performs five reads including unnecessary events/answers/activity. Preload needed contact/source fields, short-circuit unique exact-email matches, and process resumable bounded batches within the 60-second cron window.
- **Move aggregations near the data.** SQL counts or paginated full reads avoid row-limit undercounts. Build guest/event/table maps once rather than repeated nested `find`/`some` scans in reports and seating.
- **Use bulk transactional mutations.** Household seating, creation, invite changes and sync resolution should not require many independent network round trips or leave intermediate states.
- **Replace decorative media overhead.** The admin needs a lightweight static background. Measure compressed route assets and phone transfer after the change.
- **Separate freshness from rate limiting.** Process-local invalidation is not cross-instance freshness; choose explicit cache TTL/tag/shared-store behavior and keep mutation-derived numbers trustworthy.
- **Avoid unnecessary auth/query repeats within a render.** After fixing session refresh, use request-scoped memoization of admin context where appropriate. Do not cache authorization globally across users.
- **Remove maintenance traps deliberately.** Consolidate status labels/time-ago helpers/action outcome shapes, retire unused auth/session remnants and action aliases only after checking callers, and reconcile documentation. These are cleanup tasks, not substitutes for the correctness fixes.

## Decisions and production checks before handoff

1. **Name-based guest access is deliberate.** Anyone who knows an invited person's name can currently reach that household's RSVP and change it. This is not an accidental missing password step: current code explicitly chooses that tradeoff. Confirm it remains the intended policy; fix note exposure and distributed abuse controls regardless. A viewer also sees guest links and can use guest entry, so “viewer” is not an absolute prohibition on guest-side edits. Do not silently redesign guest access as part of a bug fix.
2. **Timezone needs a factual answer.** HANDOFF records `America/Los_Angeles` against a Guadalajara venue. Verify the wedding's intended zone and stored event instants; do not flip the zone alone if the instants were entered under the wrong assumption. Verify deadline and payment-day behavior after correction. No timezone data was changed.
3. **Currency and budget meaning need an explicit policy.** Separate USD/MXN until an agreed conversion rule exists. Confirm the budget ceiling, forecast, contingency, treatment of travel, all-in versus pre-tax quotes, and whether benchmark data is private in shared output.
4. **Verify deployed revision and migrations.** Check all committed migrations, sensitive RPC execution grants, and the current Vercel build. Source review does not prove production has the revocations or latest fixes. New SQL fixes must be new migrations; do not edit already-applied migrations.
5. **Verify delivery setup.** Sender/domain, reply-to, production app URL, webhook secret/events, SMTP login reliability, and recipient delivery status. A reviewed test must reach the intended admin inbox before a campaign is called ready.
6. **Verify Sheet setup and scheduling.** Credentials/sharing/range, successful latest run, cron authorization, repeat-run behavior, errors, and manual fallback. Historical “not connected” notes are not proof of current failure or success.
7. **Verify recovery.** Confirm database backups/restore availability, retention and a practical restore/export procedure. Do not assume activity logs can restore deleted data.
8. **Keep tenancy expansion separate.** Admin pages still use `defaultScope`; auth selects the first membership; many older foreign keys do not enforce composite tenant ownership. Resolve active wedding selection everywhere, tenant-consistent foreign keys, scoped service-role access and isolation tests before adding a second wedding. Membership user lookup also stops at the first 1,000 auth accounts. None of this is evidence that a second tenant is safe today.
